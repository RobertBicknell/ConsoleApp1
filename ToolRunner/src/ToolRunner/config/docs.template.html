What toolrunner is

toolrunner is a desk tool for someone who develops, tests, deploys and debugs an application that runs as docker-compose stacks. It reads a deployment folder (compose files, env files, appsettings, plugin folders), shows what is configured and what is actually running, and runs the routine operations on it as named, repeatable steps: suppress a service to debug it locally, publish plugins, swap in a debuggable image, build a new deployment for a product, generate CI pipelines, and hand a complete picture to a chat assistant.

It has three faces over one engine:

  • Command line (toolrunner ...): every operation, scriptable, with exit codes.
  • Web UI (Blazor, http://localhost:5180): the same operations with forms, a map of the system, live variables and history.
  • Copilot hand-off: one plain-text file with state and, in plan mode, everything the tool can do, so a chat assistant can answer with steps the tool then checks and runs.
Verified against what. Everything was developed without Docker, Keycloak, Azure DevOps or Artifactory available: it runs against a stand-in docker, sample folders and stubbed servers, covered by automated tests. Expect the first contact with each real system to need adjustment; the section Limits and unverified areas lists where.
Ethos: the rules the tool keeps
  • Never edit in place. A change to a compose file, env file or Dockerfile is written as a copy or an override beside the original (.toolrunner/docker-compose.debug.yml, Dockerfile.debug, docker-compose.debug-image.yml). Undo is deleting the copy. The one exception, plugin publishing, backs the appsettings file up first.
  • Read before write. The header switch starts on read-only. Every verb is declared as reads or changes; a run that contains a changing step is refused before its first step while the switch is green.
  • Everything is a variable. Paths, service names, versions, registry addresses and credentials are named values in layered files. Steps refer to them as ${NAME}; tools write results back as variables for later steps.
  • Declare once, use everywhere. Each tool describes its verbs and arguments in code. That one description validates steps, generates the JSON Schemas for editor completion, builds the UI forms, enforces read-only mode, tells Copilot what exists and produces the reference in this document.
  • Validate everything first. A workflow is checked in full (tools, verbs, saved commands) before step one runs, so a typo in step six cannot strike after step five changed something.
  • Say what was not checked. Output states what is a heuristic (plugin "loaded" from log lines, service matching by name) and what could not be read.
  • Local and remote are the same. Tools talk to a host abstraction; the same workflow runs on this machine or on a Linux server over ssh.

Quick start

1. Prerequisites

  • .NET SDK 9 or newer (the projects target net9.0), git, and docker or podman on the machine or the ssh host you will work against.
  • No Docker on this machine? sandbox\setup.ps1 and sandbox\samples.ps1 create sample deployments, and the launch profile "ui" puts a fake docker on PATH.

2. Start the UI

start-ui.cmd                      # real docker/podman; opens http://localhost:5180
start-ui.cmd D:\my-config         # the same with another config folder

From Visual Studio: project ToolRunner.Ui, launch profile ui (real containers). The profile ui is for the fake docker. To use the UI beside another solution, add the existing project to it or just run start-ui.cmd; the UI does not need to be in the solution you debug.

3. Point it at a deployment

  1. deployment tab: type the folder or press browse..., then scan. It is saved as DEPLOY_ROOT.
  2. variables tab: set APP_ROOT to the stack you work on most (commands default to it).
  3. map tab: look at the system. Press colour by running state to compare with the running containers.

4. Stay read-only until you mean it

The header shows read-only (green). Scans, the map, comparisons, logs, versions and the Copilot spool all work. Click it to allow changes before a run that edits files or starts containers.

5. The same from the command line

set TOOLRUNNER_CONFIG=C:\Claude\ToolRunner\src\ToolRunner\config
toolrunner doctor                       # are git, docker and the config reachable?
toolrunner scan dir=C:\deploy format=text
toolrunner runtime format=text          # configuration vs running containers
toolrunner digest gateway               # a workflow: condensed logs of a service
toolrunner --read-only suppress pluginhost   # refused: it would change the deployment
The UI and the command line share saved commands and workflows only when they use the same config folder. Set TOOLRUNNER_CONFIG once for your account.

6. Moving to another machine

  1. Copy the repository. Build with dotnet build.
  2. Delete config\globals.user.json (it holds this machine's paths) or edit it.
  3. Set TOOLRUNNER_CONFIG; run toolrunner doctor.
  4. Fill in what is real there: registry (REGISTRY_API...), version scheme (VERSION_*), services in globals.json.

Operations

Understand a deployment: scan, map, runtime check, compare
questionUIcommand
What is in this folder?deployment tabtoolrunner scan dir=PATH format=text
How do the services connect?map tab
Is the configuration in effect in the running containers?deployment tab, "check running containers"; map, "colour by running state"toolrunner runtime format=text

The scan reports, per stack: every environment variable and where it is defined or used (status ok, default, undefined, unused...), published ports and conflicts, bind mounts and whether their source exists, named volumes, appsettings files, and plugin assemblies listed in appsettings against the .dll files in bind-mounted folders.

The runtime check runs docker inspect on every container and tallies image, ports, mounts and environment per service: differs / missing = configured but not what runs; extra = running but not configured; taken = the port is held by another container. It tells you that something is not in effect, not why (usually: files were edited and nothing was restarted).

compare exits 0 when identical, 1 when different, 2 on trouble, and compares env, JSON and compose files by meaning.

Read logs
  • logs tab: several services side by side, level filter, text filter with highlighted matches, digest mode.
  • toolrunner digest SERVICE: repeated lines collapsed into patterns with counts, errors first.
  • toolrunner run docker verb=logs service=gateway contains="Connected to" waitSeconds=60: wait for a line (fails if it never appears). expect=absent fails if it does appear.
  • Lines from stderr are tagged (stderr); docker and git write ordinary progress there, so it is a label, not an alarm.
Take a service out of the stack to debug it locally, and put it back 
toolrunner suppress pluginhost      # needs changes allowed
toolrunner unsuppress pluginhost

suppress comments the service out of a copy of the compose file, relaxes every depends_on that points at it, writes a copy of the env file in which the consumer's host and port point at your debug session (services.NAME.debugHost / debugPort in globals.json), and starts the rest from the copies. unsuppress deletes the copies and starts everything from the originals.

Per service you describe once, in globals.json:

"services": { "pluginhost": {
    "hostKey": "PLUGINHOST_HOST", "portKey": "PLUGINHOST_PORT",
    "debugHost": "host.docker.internal", "debugPort": "5005",
    "consumer": "gateway", "logProbe": "Connected to host.docker.internal:5005" } }

With podman the host is host.containers.internal.

Publish plugins to a service

plugins tab, or:

toolrunner run plugins verb=publish project=C:\src\Acme.Loyalty dir=C:\deploy\core\plugins appsettings=C:\deploy\core\config\pluginhost\appsettings.json
toolrunner run plugins verb=loaded service=pluginhost appsettings=...

publish builds the project, copies changed files (by content hash) to the plugin folder unless that folder is the build output, and makes sure the appsettings list names the assembly (backup in .toolrunner/ beside it). Then restart the service and what depends on it, and run loaded, which reports per assembly whether the logs mention it and whether any such line is an error.

Debug a service that runs on a hardened image 
toolrunner debug-image-plan C:\src\Acme.Gateway      # reads only
toolrunner debug-image C:\src\Acme.Gateway
toolrunner restore-image gateway
  1. Finds the service the project belongs to (by project, assembly and image names; --set service=NAME to say).
  2. Picks an unhardened base: for a dhi. image the -dev variant of the same tag; otherwise same kind and .NET version, same distro family first.
  3. Writes Dockerfile.debug beside the Dockerfile: base swapped, root, ps/curl/unzip, diagnostics on, Release becomes Debug.
  4. Builds it as <repo>:<version>-debug, adds the service to a compose override file, recreates that one service.

vsdbg is not built into the image. Like Visual Studio's own container debugging, the folder %USERPROFILE%\vsdbg\vs2017u5 (its linux-musl-x64 subfolder for alpine) is bind-mounted at /remote_debugger.

Versions: what the stack is on, and source that matches

The version is the application's: the tag its images were pushed with. Base-image fragments (alpine3.20, net8.0) are never read as the version.

toolrunner versions                                # per service; the stack's version; who differs
toolrunner run version/available repo=PATH image=IMAGE
toolrunner checkout-version C:\src\plugins         # git checkout of the version's ref; refuses a dirty tree

"The version in use" is VERSION when pinned (versions tab), else the detected one. Four variables carry everything site-specific:

variabledefaultmeaning
VERSION_PATTERN\d+(\.\d+)+|latestregex: the version inside an image tag
VERSION_IGNORE(alpine|debian|...)[-_.]?v?\d+(\.\d+)*parts of a tag that describe the base image
VERSION_GIT_REFSv{version};{version};release/{version};origin/release/{version}git refs tried in order
VERSION_LATEST_REFSorigin/master;origin/main;master;mainwhat latest means in git

Example: tags like 2026.10-hotfix3 and branches rel-2026.10 need VERSION_PATTERN=\d{4}\.\d+ and VERSION_GIT_REFS=rel-{version}.

Build a deployment for a product

Creates a folder that docker compose up can start. The choices flow downwards:

product.json  ->  entities
PRODUCT_TITLE ->  product.env, container-name prefix, Keycloak realm and client prefix
version       ->  image tags in .env, plugin packages from JFrog
templates     ->  docker-compose.yml, .env, each service's appsettings.json   ({{PLACEHOLDERS}} filled in)
Keycloak      ->  realm file: clients with redirect URLs, roles, users, a privilege string naming every entity
toolrunner build plan      # what would be written; what is still to choose
toolrunner build write     # write the folder, then check it
toolrunner build fetch     # plugin packages of the version into each service's plugins folder
toolrunner build check     # variables defined, bind sources exist, plugins present, images named, no port clash
toolrunner build test      # start, verify Keycloak, deploy product.json as the admin, read the portal as the user

Keycloak is its own stack

The sample template writes keycloak/docker-compose.yml with a named docker network; the product's stack joins that network as external. Containers reach Keycloak as http://keycloak:8080 ({{keycloak.internalUrl}}); browsers use the published URL ({{keycloak.url}}). The test starts the stacks in the order template.json lists. A Keycloak that starts fresh imports the realm file; one that was already running gets the realm through its admin API.

The test, step by step

  1. docker compose up for each stack (the product's with --env-file .env --env-file product.env).
  2. Keycloak answers; its admin signs in.
  3. The realm exists; clients, roles, users, role assignments are there; each user's privilege string names every entity.
  4. The product admin gets a token and sends product.json to the config service.
  5. The end user opens the portal through the sign-in form; the page contains view instances of X for every entity.

Settings

Copilot: ask a question, or ask for a plan

history tab, or toolrunner spool. The result is one plain-text file to paste; secret-looking values are hidden in it (and only there).

Ask

toolrunner spool note="why does gateway not reach pluginhost?" last=5 scanDir=${DEPLOY_ROOT} compareRef=${REFERENCE_ROOT}

Sections: instructions, your question, the previous summary, recent runs and notes, variables, scans, comparison, files, the required answer format (spool.header.txt / spool.footer.txt). Paste the answer's CARRY-FORWARD back so the next spool includes it.

Plan

toolrunner spool intent="find out why gateway restarts"
toolrunner plan reply.txt              # check the reply against what exists
toolrunner plan reply.txt run=true     # run it (honours --read-only and --dry-run)

The cycle is STATE > INTENT > OPTIONS > PLAN > ACTION > OUTCOME. The spool gains an OPTIONS section listing every workflow, saved command and tool verb, marked [reads] or [CHANGES]. Copilot must answer with one JSON object:

{ "intent": "...", "vars": { "service": "gateway" },
  "steps": [ { "workflow": "digest", "params": { "service": "gateway" } },
             { "run": "compose/ps" },
             { "run": "docker", "with": { "verb": "logs", "service": "gateway", "tail": 200 } } ],
  "expect": "what the output shows if the intent is fulfilled" }

A plan with any unknown name, unknown or missing argument, or value nobody supplies is shown with its problems and cannot be run. In the UI, a checked plan is loaded onto the run tab as a chain; the next spool carries its outcome for Copilot to assess.

Hosts, podman, the safety switch, notes

A server over ssh

Create config/globals.NAME.json with ssh.target (user@host), optionally ssh.port, ssh.identity, and the server's own APP_ROOT as a POSIX path. Select it in the header or with --host NAME. Key authentication only.

Podman

The blue button in the header, or CONTAINER_ENGINE=podman: every docker ... the tool runs goes to podman .... Watch for: which compose provider podman compose uses (container names and labels differ with podman-compose), host.containers.internal, rootless limits on ports below 1024.

Safety switch

Green = read-only: a run with any changes step is refused before it starts; dry runs are always allowed. Command line: --read-only, --dry-run. The tool's own data (history, your variables, saved commands) is never blocked.

Notes

The box in the header, or toolrunner remark text..., puts a note into the history stream; it appears between runs and in the spool.

Extending

Your own .NET commands

Drop assemblies into plugins\ beside ToolRunner.sln (or the folder TOOLRUNNER_PLUGINS names). Each public class with a parameterless constructor that implements an interface named IDotnetTool becomes a verb of the tool dotnet.

public interface IDotnetTool { Task<Dictionary<string, string>> ExecAsync(string[] args); }

[Args(new[] { "InputFilePath", "OutputFilePath" })]
[Description("Copies a text file, upper-casing it.")]
public sealed class UpperCaseFile : IDotnetTool
{
    public async Task<Dictionary<string, string>> ExecAsync(string[] args)
    {
        var text = await File.ReadAllTextAsync(args[0]);
        await File.WriteAllTextAsync(args[1], text.ToUpperInvariant());
        return new() { ["OUTPUT_FILE"] = args[1] };       // becomes ${OUTPUT_FILE} for later steps
    }
}
  • The class name is the verb; [Args] names the arguments in the order ExecAsync reads them; a missing one arrives as an empty string.
  • Every returned pair becomes a variable. Throwing fails the step with the message.
  • [ReadOnly] lets it run in read-only mode; without it the command counts as changing things.
  • Types are matched by name: copy src\SamplePlugin\Contract.cs into your assembly. Nothing references toolrunner.
  • The folder is re-read when a file changes; files are never locked, so a post-build copy works while the UI runs.
toolrunner run dotnet verb=list
toolrunner run dotnet verb=UpperCaseFile InputFilePath=a.txt OutputFilePath=b.txt
Shell commands as steps 
toolrunner run shell verb=query "command=git -C ${APP_ROOT} describe --tags" into=DESCRIBED
{ "run": "shell", "with": { "verb": "query", "command": "my-version.cmd", "capture": "lines", "prefix": "APP_" } }
  • ${NAME} is replaced before the command runs; write the shell's own variables as %NAME%, $env:NAME or $NAME.
  • Output: stdout in into (default SHELL_OUT), exit code in SHELL_EXIT; capture=lines (every NAME=value line), capture=json (each property), regex (each named group).
  • run counts as changing; query is your statement that the command only reads.
Adding a tool in code 
public sealed class EchoTool : ITool
{
    public string Name => "echo";
    public IReadOnlyList<VerbSpec> Spec { get; } = new[]
    {
        A.Verb("say", "Log a text and return it.", A.Args(A.Str("text", "What to say.", true), A.Str("into", "Variable (default ECHO).")))
    };
    public Task<ToolResult> RunAsync(ToolContext c)
    {
        c.Log(c.Str("text"));
        return Task.FromResult(ToolResult.Success("said", new() { [c.Str("into", "ECHO")] = c.Str("text") }));
    }
}
  1. Add it to Tools/Registry.cs. Use A.Change for a verb that changes the deployment.
  2. Run toolrunner schema and toolrunner docs.
  3. dotnet test: one test checks that the arguments a tool declares are exactly the ones its code reads, another that the schemas are current.

The UI shows, but nothing is clickableStatic assets are not served. Run through start-ui.cmd or a launch profile; a published copy needs its wwwroot.
Commands "work" but nothing happens in DockerThe fake docker is first on PATH (launch profile "ui", or sandbox\run.ps1). Use "ui (real containers)".
The command line does not see what the UI savedDifferent config folders. Set TOOLRUNNER_CONFIG.
BLOCKED ... read-only mode is onThe run contains a changing step. Click the switch, or drop --read-only.
A test fails with "schema is stale"Tool specs, args.json, workflows.json or the plugins folder changed. Run toolrunner schema.
Undefined variable in a stepNothing defines that name. Set it on the variables tab, pass --set, or write ${NAME:-} if it is optional.
The runtime check says "missing" for everythingThe compose project name differs from the stack folder's name. Set COMPOSE_PROJECT.
Breakpoints stay hollowRelease build, or source at another version than the image. Use debug-image and checkout-version; untick "Just My Code".
